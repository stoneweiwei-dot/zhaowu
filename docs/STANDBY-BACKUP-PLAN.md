## 2. 三層計畫

三層都是待執行的計畫。本文件沒有建立警示、沒有建立 Cloudflare 專案、沒有改 DNS、沒有做備份或還原測試。

### 2.1 用量警示

要在網站變成 402 `DEPLOYMENT_DISABLED` **之前**，看 Vercel 用量。優先看這兩項：

- **Fast Origin Transfer**
- **Deployment Storage**

只做「網站還在不在」的檢查不夠。可連線不代表額度還夠；等到首頁已經 402，停用已經發生。傳輸量是先消耗、再反映在帳務上，事後刪部署補不回。

計畫中的觀察方式（尚未接上任何新監控）：

1. 只看唯一正式專案 `stone-zhaowu-official` 的 Hobby 用量，不為了觀察用量去多開主機或預覽部署。
2. Fast Origin Transfer 與 Deployment Storage 都要對著方案內含額度看，在接近上限時處理，而不是等 402。
3. 儲存偏高時，刪除舊部署是可考慮的儲存手段；它不抵銷已經發生的 Fast Origin Transfer。
4. 是否升級方案或付費，不在本計畫的授權內。見第 4 節。

網站恢復監控**已經由另一位助手負責**。本計畫與落實本計畫的後續改動都不得再做一套相同的站點恢復監控、排程或機器人。用量警示若要做，只補「額度將滿」這一段，並且先確認不會和既有監控重複。

### 2.2 獨立待命站

Cloudflare Pages 在 2026-11-06 被同意為**計畫中的例外**，只作主站中斷時的第二路徑。這不是平日第二正式站。

平日正式路徑仍然只有 Vercel `stone-zhaowu-official` / `zhao-wu.com`。平常不把流量切到 Cloudflare，也不把 Cloudflare 寫成 canonical。

`AGENTS.md` 2026-09-20 規定 Cloudflare 只可作開發或參考，不得變成第二正式來源。本計畫只取代其中互相衝突的那一句：Pages **可以寫進待命計畫**。例外沒有擴大到 Netlify、Replit、Sites、AppDeploy、Lovable、Floot 或其他主機。Netlify 維持封存，不得升為替代正式站。

真正做下面任何一件事之前，站主 Stone 必須**再批准一次**。寫下本計畫不算那一次批准：

- 建立或登入 Cloudflare 帳號
- 建立 Pages 專案或開始建置
- 把網域、DNS 或正式流量切到待命站
- 為待命站付費或提高額度

待命站不得依賴「同一個已刪除或空白的資料庫」：

- 不指向已刪除的 `plgpxusmemnmzckbwtiv`
- 不把 `zhaowu-core` 在 2026-11-06 的 0 列公開表當成已恢復的使用者資料
- 不把程式碼或 `CREATE TABLE` SQL 當成資料還原

啟用前先驗證相容，順序固定：

1. 最低能力：主站不可用時，待命站能送出**公告**，並提供**基本內容**。
2. 這一步成立之後，再評估完整功能能不能在不靠已刪除或空白資料庫的條件下運作。

未通過第 1 步，不進行網域切換，也不把完整功能標成待命站已具備。

### 2.3 資料備份

Git 裡的程式，或一份 `CREATE TABLE` SQL，**不是**使用者資料備份。結構在，人、報告、圖與登入可以仍然不在。

計畫要覆蓋的三類（尚未在本文件宣稱已經備妥）：

| 類別 | 計畫要保留的內容 | 目前不得宣稱的事 |
|---|---|---|
| 資料庫 | 業務資料；若平台允許，一併包含 auth 使用者，且要能還原 | 不得把 schema／設定檔說成使用者傾印 |
| 圖片與儲存 | 正式站仍需要的圖片與其他儲存物件 | 不得把倉庫裡的原始碼路徑當成 Storage 已備份 |
| 設定 | 復站所必需的設定項目清單 | 不得把密鑰、權杖或服務角色金鑰寫進本倉庫 |

然後要**測試還原**。還沒還原成功的備份，狀態就是未驗證。

截至 2026-11-06 可以寫明的現況只有這些：

- Dropbox `/Zhaowu-Backup/` 可作冷備份與人工資產保存，不在正式站 runtime。它是結構性存放，不是已驗證的使用者資料傾印。
- 既有 schema／設定備份同樣是結構性的，還原未經驗證。
- `plgpxusmemnmzckbwtiv` 已刪除且無法還原。對那個專案再跑 SQL，不會把使用者、報告或檔案找回來。
- `zhaowu-core`（`gyisxbkjzvdretbqzeuw`）當時健康且公開表為 0 列。健康不等於裡面有舊正式站的資料。

本文件不指定新的傾印檔名、桶名或試用額度。那些位置若尚未經站主確認並實際還原，就不存在於這份計畫裡。

還原測試的目標（尚未執行）：在不覆蓋正式站、不改 DNS 的隔離條件下，確認一份備份至少能讀回資料庫內容、該份備份所含的 auth 使用者、儲存物件，以及復站所需設定。做不到的段落要明確標成缺失，不能靠「有表結構」補上。

重建資料庫、灌回資料或新開 Supabase 專案，仍要站主 Stone 另行明示批准。
